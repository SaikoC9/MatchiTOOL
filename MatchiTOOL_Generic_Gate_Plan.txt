GOAL
Any plugin that has its own local web page (AdGuard Home, OpenWrt-style panels, others) gets the same protection from MatchiTOOL:
- The page's own login cookie (often 30 days) never reaches the browser.
- The browser holds one session-only cookie that works only while the MatchiTOOL console session lives.
- The page asks for ITS login again after: MatchiTOOL sign-out, session expiry, password change, host restart, idle timeout.
- Optional (off by default): also after the last page of the tab closes.
Written once in MatchiTOOL. A plugin only declares what it needs.

WHAT EXISTS TODAY (starting point, from the AdGuard work)
- AghGateProxy.kt : plain-JVM proxy (no Android classes). Ticket entry, gate cookie, cookie stripping, html script injection,
  hb/bye tab logic, sweep, upstream logout. Tested by hand against a fake upstream.
- AghGate.kt      : Android wrapper (lazy start, tickets, sweep hooks).
- /api/agh/gate   : route that returns a one-time ticket.
- AghDoor.kt      : hooks sweepAsync / closeAll.
- Plugin 0.9.7    : Open button uses the ticket.

PRINCIPLES
1. Keep the proxy core free of Android classes so it runs in plain JVM unit tests.
2. Fail closed: no valid gate, wrong address, dead console session = 403, never a pass-through.
3. Off by default. Nothing listens on any gate port until a plugin asks for it (first Open).
4. The plugin declares, MatchiTOOL enforces. A plugin cannot weaken the rules (no "skip auth" option).
5. Plain HTTP pages first. Anything that cannot work behind the proxy must say so clearly, not break silently.

PHASE 0 - Decisions (half a day, no code)
----------------------------------------------------------------------
Decide and write down:
a) Declaration format in the plugin header, for example:
     // @matchi-gate name=adguard port=3000 logout=/control/logout idle=3600 tabclose=off
   Fields: name (id, [a-z0-9-]), port (target on 127.0.0.1), logout (path to call with the target cookie, optional),
   idle (seconds, default 3600, min 300, max 43200), tabclose (on/off, default off).
b) Gate port rule: target port + 1? Fixed range 3100-3199 chosen by MatchiTOOL and stored per gate name? (Recommended: MatchiTOOL
   picks from a fixed range, stores name->port, returns it in the ticket reply. Plugin never hardcodes it.)
c) Which cookies to hold server-side: all Set-Cookie from the target (recommended), not only one name. Cleared when the target
   clears one (Max-Age<=0 or Expires in the past).
d) Max gates at once (suggest 4) and max sessions per gate (suggest 16, already in code).
DECIDED (by the user, 2026-11-18):
a) Full header line: @matchi-gate name=adguard port=3000 logout=/control/logout idle=3600 tabclose=off  (only name and port required).
b) MatchiTOOL picks the gate port from 3100-3199, remembers it per gate name, returns it with the ticket.
c) The proxy keeps ALL cookies of the target on the router (dropped when the target clears them).
d) Defaults: tabclose=off, idle=3600 s, at most 4 gates open at once.
Phase 0 is closed; start with Phase 1 and 2 together.

PHASE 1 - Generalize the proxy core (JVM only)
----------------------------------------------------------------------
Files: AghGateProxy.kt -> WebGateProxy.kt (rename), AghGate.kt -> WebGate.kt.
Changes:
1. Constructor takes a config: listenPort, upstreamPort, logoutPath?, idleMs, tabClose (bool), consoleValid.
2. Cookie jar instead of one agh_session: Map<name, "name=value"> per gate; send all as Cookie header upstream; update/clear from
   every upstream Set-Cookie; never forward Set-Cookie to the browser.
3. Logout call uses config.logoutPath (GET). If null, skip the call (the browser still loses access because the jar is dropped).
4. tabClose false: do not inject the script, no hb/bye, no tab map. tabClose true: current behavior.
5. Idle = no proxied request for idleMs (replaces the fixed 1 h constant).
6. Location rewrite uses the configured upstream port (already does).
7. Handle HEAD and 304 correctly; keep the 24 MB response cap and the 2 MB request cap; add a clear 502 text.
8. Chunked REQUEST bodies: reply 411 with a clear message (already). Document it.
Done when: all Phase 1 tests (below) pass on plain JVM.

PHASE 2 - Tests (do this together with Phase 1, not after)
----------------------------------------------------------------------
New file: app/src/test/java/com/matchi/tool/WebGateProxyTest.kt (same style as the other tests; local fake upstream with ServerSocket,
no Android). Cases:
- No cookie -> 403. Wrong address with a valid cookie -> 403. Dead console session -> 403 and upstream logout called once.
- Ticket works once only, expires after 60 s (fake clock), is bound to the address.
- Upstream Set-Cookie never reaches the browser; the next request carries it upstream; clearing cookie empties the jar.
- Multiple cookies kept and sent.
- Idle timeout logs out and drops the jar.
- tabClose on: bye + grace logs out; a new hb inside the grace does NOT log out; stale tab after 150 s logs out.
- tabClose off: html is not modified.
- Redirect Location with the upstream host is rewritten.
- Request > 2 MB -> 413. Chunked request -> 411. Upstream down -> 502.
- Concurrent requests (20 threads) do not deadlock.
Use the injectable clock (already a constructor parameter) so no test sleeps.

----------------------------------------------------------------------
RISKS AND WHAT TO DO ABOUT THEM
----------------------------------------------------------------------
- Pages with WebSockets or server-sent events do not work behind this proxy. First version: plain HTTP only. Detect "Upgrade:" requests
  and answer 501 with a clear text.
- Pages that use absolute URLs to the original port break. The Location rewrite covers redirects only. Document it for plugin authors.
- All requests reach the target from 127.0.0.1, so the target's own brute-force limit becomes global (one wrong-password burst
  locks everyone). Acceptable; mention it in the docs.
- Large responses are buffered in memory (cap 24 MB). Fine for admin pages; not for downloads. Streaming can be a later phase.
- A bug in the proxy must never open a page without a login: tests for "403 when anything is missing" are mandatory (Phase 2).
- Plain HTTP on the LAN: the password still travels unencrypted, same as before. If the console runs over HTTPS (Tls.active), a later
  phase can serve the gate port over the same certificate.
- Android parts were never compiled in this work (only the JVM proxy core was compiled and run). Build in CI first.
