MatchiTOOL - PHASE 3 TO-DO  (written after reading code and the Phase 2 device results; Phase 2 closed 2026-11-13)
"Delete plugin" also undoes what the plugin changed OUTSIDE its own files - even when it declared nothing
=================================================================

GOAL
  Phase 2 ends what a plugin STARTED (processes). Phase 3 undoes what it LEFT BEHIND in the system.
  Seen on the F50 (Phase 2 test M, Bypass without headers): the sweep ended both watchers, but these stayed until a reboot or by-hand cleanup:
    - the firewall chain UFI_DPI (-N UFI_DPI, a jump from POSTROUTING, TCPMSS rules)
    - the pin /sys/fs/bpf/ttl_bpf
    - the boot entry /data/local/matchitool/boot.d/20-bypass-ttl.sh  (the watcher would start again at the next boot)
    - its folders /data/local/ufi_ttl and /data/local/ufi_dpi (no ledger path, so nothing erased them)
  With the @matchi-uninstall headers all of this was removed (M part 1). Phase 3 closes the same gap for a plugin WITHOUT headers, where the host can learn
  what to undo. Phase 3 never guesses: it undoes only what the host SAW the plugin's own commands create.

FACTS FOUND IN THE CODE
------------------------------------------------------------------
Q1  The ledger (PluginTrace.kt) has three line kinds: "P /path" (write targets read from command TEXT), "E side effect" (a plain word list), "U uploaded name".
    The E line says only "firewall rules" or "boot script lines". It stores NO chain name, NO table, NO tool (iptables / ip6tables), NO boot file name.
    So today the host cannot tell WHICH chain a plugin made. pluginSideEffects() is a regex on the command text.
Q2  pluginWriteTargets() sees redirections, tee, mkdir, touch, cp / mv / install / ln, dd of=, curl -o, wget -O, unzip -d, tar -C, sqlite3. A path built inside a
    script file the plugin wrote is NOT seen (same limit as Phase 2, P2). The Bypass boot file is written by a helper script, so it may or may not be in its ledger.
Q3  checkPluginDataPath (PluginPaths.kt) refuses to erase anything under /data/local/matchitool ("MatchiTOOL's own folder is protected"), so a ledger path in
    boot.d is never erased today even when it is the plugin's own file. Erasing is only allowed under /data/local (not protected names), /data/local/tmp, /sdcard.
    [FACT] The Phase 1 doc comment says boot files "live in the shared boot.d folder" and are checked, not erased, by Phase 1 (@matchi-boot + a file test).
Q4  The boot runner (HostService.kt ~360) runs boot.sh and then every boot.d/*.sh, each as root, with a 25 s limit. A leftover file there runs again at every boot.

PROPOSED DESIGN (all [DECISION] until answered)
------------------------------------------------------------------
A  Ledger gets two new line kinds, written when a command passes through the host with a plugin name (same sites as the Phase 2 tag):
     "C table chain tool"   from  iptables|ip6tables [-t TABLE] -N CHAIN   (chain name letters, digits, _ and -, at most 28 characters)
     "J table parent chain tool"  from  -A|-I PARENT ... -j CHAIN  where CHAIN is a chain this plugin created (so a plugin cannot make the host touch a system chain)
     "B /data/local/matchitool/boot.d/NN-name.sh"  from a write target in boot.d whose name matches ^[0-9]{2}-[A-Za-z0-9._-]{1,60}\.sh$
   Only text the host SAW. A chain made inside a helper script is not recorded (stays in LIMITS).
B  Undo of a recorded chain, run as root on "Delete and stop", AFTER the sweep (so no watcher re-adds rules): delete every rule that jumps to the chain
     (iptables -t T -S | rules containing "-j CHAIN" -> -D), then -F CHAIN, then -X CHAIN. Both iptables and ip6tables if both were recorded.
   The script is built by the host from the recorded names only (validated characters), like the sweep kill script; no plugin text is put in.
C  Undo of a recorded boot.d file: remove it only when it passes Q8 (own ledger, safe name, regular file, no other plugin names it). Everything else is listed, not touched.
D  The dialog lists every undo BEFORE it happens ("It will also remove the firewall chain UFI_DPI (iptables, mangle) and the boot file 20-bypass-ttl.sh"), and a hash
   of the list is sent back like sweepHash: what you saw is what runs.
E  Verify after: chain gone (iptables -S), boot file gone. The report says "undone" only when the re-check ran. Failure keeps the plugin (same rule as Phase 1/2).
F  "Disable and stop": the plugin's toggle gets a stop (sweep + declared commands + the undo above) WITHOUT deleting the plugin or its data.
