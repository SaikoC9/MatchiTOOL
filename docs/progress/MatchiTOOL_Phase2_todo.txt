"Delete plugin" also stops what the plugin started - even when the plugin declared NOTHING
=================================================================

GOAL
  Phase 1 stops what a plugin DECLARED (@matchi-uninstall headers). A plugin with no headers
  still gets "declares no stop commands. Anything it started may keep running" (test B).
  Phase 2 closes that gap with two things:
    (1) a process sweep: find the processes a plugin started and end them, using
        - a TAG   (an environment marker the host adds to the plugin's own commands),
        - a PIDFILE the plugin wrote (the ledger already records written paths),
        - a COMMAND-LINE match against files the ledger says the plugin wrote.
    (2) a JavaScript hook: a plugin can register code that runs when it is deleted.

FACTS FOUND IN THE CODE
------------------------------------------------------------------
P1  Attribution is best effort. A trusted plugin's root commands carry the header
    x-matchi-plugin, taken from the plugin script's stack frame by the page (index.html
    ~3555; only for /api/shell, root_shell, user_shell, upload). A Request object or a
    command from eval'd text loses it. The page sets the header only if the plugin did not
    set one, so a plugin can name ANY plugin. A SANDBOXED plugin's shell calls go through
    /api/plugins/call, where the host itself knows the name (WebRoutesPlugins.kt ~463):
    reliable there. Conclusion: the sweep is best effort, never a security boundary.
P2  The ledger (PluginTrace.kt) has no process data. "E background processes" is only a text
    regex on the command (nohup|setsid|trailing &). It stores no PID, no tag, no pidfile.
    "P" lines are write targets seen in the COMMAND TEXT: "echo $! > /x/beat.pid" gives
    "/x/beat.pid"; a pidfile written inside a script the plugin created gives nothing.
P3  RootShell runs each script as its own process group ("setsid sh", launcher() ~126) in a
    pooled su session, output to a temp file. A background job the script leaves behind keeps
    running after the script ends (Phase 1 test A: the heartbeat survived). The group/tree
    kill (killScriptTree ~138-153: SIGSTOP the tree, kill -9 -- -PGID, kill -9 leader) runs
    only on TIMEOUT.
P4  Lesson from Phase 1 tests A/C: a plain "kill" on a subshell loop with a foreground
    "sleep 30" did not end it at once; kill -9 did. A sweep must freeze the whole tree first
    (like killScriptTree) so a parent cannot respawn a child, then KILL. "ps -A -o PID,PPID"
    is already used by RootShell; "ps -A -o ARGS" works on the F50 (Bypass test).
P5  SELF-KILL HAZARD. A sweep run through RootShell has the matched text inside its own
    command line, and its parents (su session, the shell) too. Any "match by command line"
    must exclude the sweep's own PID chain. Also never touch: PID 1, kernel threads, the
    MatchiTOOL app process (com.matchi.tool) and the root session pool.
P6  Phase 1 parts to REUSE (PluginUninstall.kt): the 60 s clock STOP_TOTAL_MS, runStopCommands,
    verifyStop / StopVerify (leftovers, notChecked), stopReport / StopReport, stopMode,
    stopPlanHash, pathsOverlap / pluginsUsingPath / commandPaths (the "do not break a newer
    copy" guard), the D3 rule "failed stop keeps the plugin", "Delete without stopping", and
    the rule "never report stopped when a check did not run".
P7  stopMode() today: no stop flag -> as before; empty plan -> as before. So a plugin without
    headers never reaches the stop code. Phase 2 must change that on purpose (DECISION D2).
P8  The shared-copy case is the dangerous one for Phase 2 too: the OLD copy of a plugin
    starts the job, the NEW copy is installed, the OLD one is deleted. A tag says "started by
    OLD" and would kill the process the NEW copy now relies on (test C again). The sweep needs
    the same shared-path guard as Phase 1.
P9  Plugin loading: a trusted .js plugin is a <script> in the page (index.html loadPlugins
    ~5504); a sandboxed one is an iframe with a message bridge; the host-side bridge ops are
    only at, router.get, shell (/api/plugins/call). There is NO hook op today. A DISABLED
    plugin never ran this session, so it cannot have registered a hook. .html (UFI-TOOLS)
    plugins are injected with ufiInject.
P10 The host cannot run plugin JavaScript. A hook runs in the browser BEFORE the delete
    request; the host cannot see whether it worked. The only trustworthy result is the host's
    own re-scan afterwards (same idea as the check command in Phase 1).
P11 shellDanger does not block kill/pkill for plugins. A trusted hook can send any command,
    and it cannot be listed word for word in the dialog (Phase 1 shows every command). A
    sandboxed hook can only run commands the person granted (exact match), so it stays
    reviewable.
P12 The sweep script is built by the HOST, not by the plugin, so it needs no per-plugin
    approval; but it still needs the root gate + password (same as Phase 1) and an audit line
    ("plugin-sweep").
UNVERIFIED (device)
  - /proc/PID/environ is readable by root on the F50 and holds the marker of a child started
    with nohup/setsid.
  - (Step 2 probe) tr with '\000' escapes, "stat -c %u", "grep -m1", and "${20}" in the F50's sh; the probe reads /proc itself
    instead of ps, so the ps ARGS column question below only matters for RootShell's own use. Time the probe: it must stay well under 15 s.
  - ps -A -o PID,PPID,ARGS column behaviour (long ARGS, truncation) and the cost of reading
    /proc for every process inside the 60 s clock.
  - The session shell in the pool is persistent; the script runs in a child "sh", so an
    "export" inside the script should not leak into later commands. Check, and use a subshell.

LIMITS (say them in the docs, do not hide them)
------------------------------------------------------------------
  - The tag only exists on commands MatchiTOOL saw with a plugin name (P1). A process started
    some other way, or one that clears its environment, is only found by pidfile or command line.
  - Command-line matching can miss a renamed binary and can match too much; that is why it is
    shown first and limited to ledger files (D1).
  - A plugin can lie about its name (P1); the sweep protects the user from a forgetful plugin,
    not from a hostile one.
