DEVICE TESTS (F50, root). The app's folder: /data/data/com.matchi.tool/files
Log lines: Log Catcher in the web page, or:  su -c 'logcat -d | grep -E "LiveSampler|BinaryCheck|WebServer"'

P4-1  the program is installed and matches the build
    su -c 'cd /data/data/com.matchi.tool/files && sha256sum matchi-sampler && ./matchi-sampler -version'
  Expect 82bc92bc...4cc6 and "matchi-sampler 1.0 (MatchiTOOL)". Full diagnose, "bundled binaries": 6 lines, all ok.

P4-2  the program on its own prints the line (tools/sampler/README.md has the same)
    su -c '/data/data/com.matchi.tool/files/matchi-sampler -rounds 3 -sleep 1'
  Expect three @L1 lines, the first with s: filled. Then: su -c '... -rounds 1 | head -c 200' must exit quietly.

P4-3  setting OFF (the default) is exactly the old behaviour
  Open the Live panel. The "Fast sampler" button shows "Off". Values appear. On the device:
    su -c 'ps -A | grep -E "matchi-sampler|sh /dev/fd/3"'
  Expect an "sh /dev/fd/3" process and NO matchi-sampler process.

P4-4  switch ON in the page
  Click "Fast sampler: Off". Expect the toast "Fast sampler on", the Live values keep updating (no blank gap longer than 2-3 s), and:
    su -c 'ps -A | grep -E "matchi-sampler|sh /dev/fd/3"'
  Expect a matchi-sampler process and no "sh /dev/fd/3" for the Live reader. Compare the numbers (CPU %, core speeds, zone names,
  memory, load) with what the shell loop showed a minute ago: same zone names, same cores, same kind of values.

P4-5  switch OFF again
  The loop is back, matchi-sampler is gone from ps within a few seconds.

P4-6  closing the page stops the program (nothing keeps running as root)
  With the setting on, close the Live tab / the browser. After about 15 s:
    su -c 'ps -A | grep matchi-sampler'
  Expect nothing. Then force-stop the app while the Live panel is open: matchi-sampler must be gone within a few seconds too.

P4-7  the way back and the refusals
  a) Fallback: with the setting on, make the program unusable but keep its hash (cannot be done by editing, the hash would change),
     so use this instead: su -c 'chmod 000 /data/data/com.matchi.tool/files/matchi-sampler'  (it is still the same bytes, but cannot run).
     Restart the reader (turn the setting off and on). Expect after ~3 s: Live values come back from the shell loop, and the log has
     "matchi-sampler gave no readings 2 times, using the shell loop". Then: su -c 'chmod 755 /data/data/com.matchi.tool/files/matchi-sampler'
     and open the Live panel again (stop + start): the program is used again.
  b) Changed file: su -c 'echo x >> /data/data/com.matchi.tool/files/matchi-sampler'. With the setting on, restart the reader.
     Expect the log "matchi-sampler was refused ... removed", the file gone, and the shell loop running. The button disappears
     (not installed). Stop and start the host in the app: the file is back and the button returns.
  c) With the file missing the page must not offer the button, and POST /api/live/engine {"fast":true} answers 409.

P4-8  CPU before / after (the point of this phase)  - plan step 3
  Same conditions both times: screen off or app in the background, one browser tab with the Live panel open in Live (1 s) mode,
  no plugin or AT console in use, same room temperature.
    adb push scripts/measure_live_cpu.sh /data/local/tmp/
    # setting OFF:
    adb shell su -c 'sh /data/local/tmp/measure_live_cpu.sh 300'
    # setting ON (click the button, wait 20 s):
    adb shell su -c 'sh /data/local/tmp/measure_live_cpu.sh 300'
  It prints the reader's CPU and the app's CPU as "percent of one core" over 300 s. Run each twice and take the lower of each pair.
  Optional cross-check: su -c 'top -b -n 1 -o PID,%CPU,ARGS | head -20' during each run.
  Done when: same values as the shell version (P4-4) and the reader + app total is lower with the setting ON.
  If it is NOT lower, say so in CHANGELOG.md and leave the setting off by default (it already is).

KNOWN LIMITS
- The program replaces only the reader's script. The parse and snapshot code in Kotlin (LiveScript.parse, LiveSnapshot) is the same, so
  the app's own CPU for parsing does not change; the saving is the processes the loop started every second (sleep, subshell reads).
- If the program prints readings but wrong ones, the fallback does not notice (it only looks for "no reading at all"). P4-4 is the check for that.
- A new setting value takes effect at once only while a reader runs; otherwise at the next start of the Live panel.

ROLLBACK
Setting off = the old shell loop (the default). To remove the feature: revert the commit; the shell loop code was not changed.
